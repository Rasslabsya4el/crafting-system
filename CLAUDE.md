## Agent skills

### Issue tracker

Issues live in GitHub Issues for `Rasslabsya4el/crafting-system` (via the `gh` CLI). See `docs/agents/issue-tracker.md`.

### Triage labels

Default vocabulary: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`, plus `deferred` and `needs-rewrite` (see "Direction since 2026-11-13"), and two priority marks set by the triage of 2026-11-20: `critical-path` (the ticket stands between today and a heavy reference craft giving a proved, playable plan; these are taken first) and `after-beta` (true, harmless to leave, not needed for the beta; taken only when nothing else waits). A `ready-for-agent` ticket with neither mark is needed for the beta. See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: one `GLOSSARY.md` and `docs/adr/` at the repo root. See `docs/agents/domain.md`.

## Direction since 2026-11-13

The owner reset the direction on 2026-11-13, in a retro held in the dispatcher chat (his standing chat that starts the ticket agents, also called the main thread; not the heavy-run dispatcher script). His decisions are rules OR-35 to OR-52 of `docs/owner-rules.md`; they override any older ticket, ADR or note that disagrees, and a ticket's chat reads them there. What a chat needs before it opens that file:

- **Goal:** a public website in November 2026 that plans a route for the item a user builds, and stores the routes for other users (OR-35, OR-36).
- **Methods:** the beta is batches B1, B2 and B3 without its recombinator, each built end to end; every other method is deferred (OR-37 lists them). A ticket that mixes a deferred method with one in scope is done for the part in scope only.
- **Code:** planning lives in a planner module of its own with one entry (target and prices in, plan out); `cli/` only parses arguments and prints. Every method goes through one search (the envelope search) with a lower bound per method. The full graph walk, the packed walk, bound pruning and the approximate ladder are being retired: nobody extends them, tunes them or writes tests against them. Tests go through the planner's entry, and whole-page HTML goldens shrink to one or two. This design is the dispatcher chat's, under OR-50; it is not the owner's wording.
- **Limits and the stop:** OR-39 and OR-40. A planner limit is a setting of the machine a run is on, never a constant sized for a GitHub runner; the heavy-run timeouts and the CI caps are another matter.
- **Tickets:** an issue labelled `deferred` or `needs-rewrite` is not taken. `needs-rewrite` means its text prescribes the old pipeline: the dispatcher chat rewrites it (its audit comment of 2026-11-13 says what must change) and then removes the label. A ticket without those labels that still names a retired path, or a file under `cli/` for planning code, is built through the planner module and the one search all the same, and the chat names in its PR each place where it left the ticket's text.
- **Since 2026-11-16 (OR-53 to OR-57):** the work is on the planning system only: no chat builds the site's pages, front end, deploy or hosting, cuts tickets for them or asks the owner about them until he says (OR-53). Nothing of the beta is cut for a date, and nobody asks him to pick one (OR-54). The beta's bar is every B1 to B3 method on any target within the limit (OR-55). A site user's plan is computed on our server, not in the user's browser (OR-56). The repo installs and runs on any Windows or Linux machine, which is why a PR lands on Ubuntu and Windows (OR-57); the machine and the system of the site are not decided.

## How work is split

One ticket is done by one ticket agent, start to end: it reads the ticket, codes, tests, gets the reviews, runs the heavy runs and opens the PR. The dispatcher chat (the owner's standing chat) cuts the tickets, starts one background agent per ticket, each in a worktree of its own (`.claude/worktrees/tN`), and lands the PRs. A ticket agent never runs `gh pr merge` in any form, never pushes to `main` and never starts an integration run: only the dispatcher chat lands (the rule was broken twice, and a broken `main` was the result). "The main chat" in this file and in `docs/ci.md` is whoever does the step a sentence names: the ticket's agent for the code, the tests, the reviews, the heavy runs and the PR; the dispatcher chat for the integration run, the merge and what follows it.

Ticket agents run in parallel on the server, any number of them: asked how many tasks may run at once there, the owner wrote «Сколько угодно сразу, теперь нет никаких ограничений» (2026-11-17; "Any number at once, there are no limits now"). What still holds a ticket back is the two queues below and the load rule of "Heavy runs". A ticket's code is still never cut into pieces for coder helpers (#722): what an agent pays for is mostly reading, and a coder helper would read again the code the agent already read to brief it. Four helpers in `.claude/agents/` stay, because each reads much and hands back little, or reads little and saves a larger cost:

- `finder` (Haiku 5.5): wide reading and search; the chat keeps only its facts. It is used instead of the built-in Explore agent, since it answers in a short list of facts with `file:line`.
- `checker` (Sonnet 5.5): one review of a PR against its ticket before it lands.
- `crafter` (Sonnet 5.5): reads one route page against its target as an experienced Path of Exile player does, with the written checklist of its file, and answers with what a player would call wrong, step by step, or that the route is what a player would do (#888). Tests do not see these faults and the owner does not read route pages himself.
- `auditor` (Opus 5.5): the owner's check on the dispatcher chat itself (owner, 2026-11-22: «Уже третий раз подряд я прошу сделать ретро и оказывается что 90% времени мы стоим на месте»; "For the third time in a row I ask for a retro and it turns out that 90% of the time we stand still"). The dispatcher chat starts it every three hours and after each landing; it reads what landed, what runs and the scoreboard of the reference crafts, appends its verdict and at most five orders to `.claude/scratch/audit/journal.md`, and hands back a plain summary in Russian for the owner. The dispatcher chat carries out each order or writes in its log why not, and gives the owner the summary unchanged at his next message. It reads much and hands back little, so it is a helper; it runs on Opus because it judges.

A helper prompt names its ticket (`#N`) and the files, branch or worktree. An agent does one ticket, and tickets wait for each other in two cases (the cap of five tickets with heavy runs at once, from retro #712, went with the PC: on the server the load rule of "Heavy runs" decides when each run starts):
- Tickets that change the same files share a queue: the dispatcher chat starts the later one after the earlier one has landed.
- PRs that change the recorded numbers of one route (goldens, fixtures, packed values) share a queue: the later one may build its code, but its heavy runs and re-records start after the earlier one has landed. The dispatcher chat names the route when it cuts the ticket.

A root fix that also changes data lands as two PRs: first the mechanism, with tests on hand-worked numbers; then the data (a new snapshot) and its re-records.

The owner's rules are in `docs/owner-rules.md` (`OR-1`, `OR-2`, ...). A ticket that touches targets, routes, prices or pages names the rules from that file it must follow (the dispatcher chat writes them into it when it cuts the ticket), the main chat cites them in its PR, and the `checker` reviews every change against the file as well as against its ticket. A PR's open points (findings, placeholders, places that contradict a rule) are not left in its prose: the PR's author files them as issues before asking to land, the `checker` confirms they are filed, and the main chat lands nothing without them. A fault the `crafter` finds, and a method it lists as left out that a player would use, is such an open point: the PR fixes it when the PR caused it, and otherwise the main chat matches it to an open issue or files it (label `ready-for-agent`, or `deferred` when it concerns a deferred method), and names the issue in the PR.

The dispatcher chat also runs the `crafter` over the current page of every reference route (`REFERENCES` in `src/crafting_system/cli/_benchmark.py`; the V01 smoke test is not one, #901) at each checkpoint (each time it reports the state of the routes to the owner; the page is the recorded one, or the one the checkpoint's own benchmark run built), matches or files its faults the same way, and gives the owner in the chat a short digest (per route: the target, the cost against the guide, the crafter's verdict), with the full page only where the crafter doubts or the cost is far from the guide (OR-46).

Model: every agent the dispatcher chat starts for a ticket or a measurement runs on Opus 5.5, never on Fable: the owner wrote «Можно пожалуйста всех сабагентов перевести на опус? Я не разрешал фейбл» (2026-11-18; "Can all the subagents please be moved to Opus? I did not allow Fable"). So the dispatcher chat names the model when it starts one (`model: "opus"`), because an agent started with no model named takes the chat's own (the dispatcher chat's observation: the agent of #1278 ran on Fable 5.2). The dispatcher chat itself runs on the model the owner sets for it with his `/model` command (Fable 5.2 on 2026-11-17 and 2026-11-18; he stated no rule with it). The last rule he stated for the chats is Opus 5.5 with effort medium (2026-11-10: one model, no hand-offs; from 2026-11-13 to 2026-11-14 everything ran on Fable 5.2, OR-51, and he ended that on 2026-11-14). The helpers keep their own models (`finder` Haiku 5.5, `checker` Sonnet 5.5, `crafter` Sonnet 5.5, `auditor` Opus 5.5), set in their own files under `.claude/agents/`, so a chat or an agent starts them with no model named; that his message leaves them as they are is the dispatcher chat's reading (none of them runs on Fable).

Landing a ticket: review comes before the expensive part. Once the code and its quick tests pass, the main chat starts the `checker` on its branch, which reviews that head, and the main chat checks the fix round from its diff (a new mechanism in it goes to the `checker` again). A PR that changes a route's recorded numbers or its page also gets the `crafter` at this point, next to the `checker`: one review per changed page, of the page as the branch builds it. When a quick local build gives that page, the review comes here, before the heavy runs; when only a heavy run can build it, the review is of the re-recorded page, before the PR lands. Either way the main chat fixes its faults or files them, and names them in the PR. Only then do the heavy runs and golden re-records run; a code change after them runs them again. The ticket's agent opens the PR with `Closes #N`, waits until the PR's own CI is green and reports the PR ready to land; the dispatcher chat merges it once the integration run (a `workflow_dispatch` of `ci.yml` on an `integ/...` branch holding `main` plus the PRs) is green on Ubuntu and Windows, the `checker` has passed it, the `crafter`'s faults on its changed pages are fixed or filed, the dispatcher chat has checked its re-recorded numbers from the diff, and its tests cover the ticket's "Done when"; a PR's own CI runs Ubuntu only and is feedback while it works, and an agent that needs Windows early asks the dispatcher chat, which dispatches `ci.yml` on its branch; then it runs the tests on `main` and adds the ticket to the map's decisions. Nobody asks the owner about Auto-fix or merging. A push to `main` starts no CI run: `main` is verified by the integration run, whose tree must equal `main` after landing (`gh workflow run ci.yml --ref main` tests it on demand; `docs/ci.md`). A process-text PR, one whose every changed file is a `.md` file under `CLAUDE.md`, `README.md`, `docs/ci.md`, `docs/agents/`, `.claude/agents/`, `.claude/skills/`, lands with no integration run, since no test reads those files (owner, 2026-11-10); other `.md` files (owner rules, ADRs, research notes, goldens) are read by tests and take the full run. The `checker` still reviews it, and the main chat merges it once that passes; the next integration run tests that `main`. The check and the list: `docs/ci.md`, "Landing a pull request".

One ticket per agent. The state of the work lives in the GitHub issues and in the agent's handoff file (`.claude/scratch/handoff-tN.md`: what is done, what is decided and why, what is next, the results of its runs), which the agent keeps current, so a fresh agent continues from it and a cleared chat loses nothing.

Everything this repo needs lives inside this folder: worktrees in `.claude/worktrees/`, scratch files and run output in `.claude/scratch/`.

The main folder (`/root/projects/crafting system` on the owner's server, where the chats work since 2026-11-17; before that `C:\Coding\Crafting system` on his PC) stays on the branch `main`, because every new chat reads this file and `.claude/agents/` from it: a chat never checks out another branch or commit there (it reads one with `git show` or works in a worktree), and after merging a PR it runs `git pull --ff-only` there. From 2026-11-07 to 2026-11-10 it sat on an old commit, and new chats kept the coder helpers this file had already dropped (#722).

## Heavy runs

**Heavy runs go on the owner's server** (owner, 2026-11-17): the machine the chats work on, Ubuntu 24.04 with 24 cores and 60 GB. A sweep, a solve, a measurement, a benchmark, a golden re-record or the full suite runs there from the ticket's worktree, as a background command of the main chat (its exit is the notification), with its output under `.claude/scratch/`. Nothing heavy runs on the owner's own PC. A server run keeps these rules:

- **Data.** The game data is one shared folder: `export CRAFTING_CACHE_DIR="/root/projects/crafting system/.claude/scratch/crafting-cache"` (`uv run --no-sync python -m crafting_system.data fetch` fills it again when it is gone). A new worktree gets its packages with `uv sync --locked --extra web`.
- **Cores.** The agents share the machine, and the owner gave all of it to this work: «Ты можешь юзать все мощности сервера для тестов и прочего. Там почти ничего больше нк происходит» (2026-11-17; "You can use all the capacity of the server for tests and the rest. Almost nothing else happens there"). One run takes at most 16 processes, and starts only when the 1-minute load (`uptime`) plus its processes is at most 22; otherwise the agent starts it later (a background `until` loop that ends once the run has started). The two figures are the dispatcher chat's. A quick, targeted test is one process and runs at any time.
- **Threads.** Before any run, a quick test included: `export OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 NUMEXPR_NUM_THREADS=1`. Without them one Python process opens a 24-thread math pool and takes about 7 cores (the load reached 76 on 2026-11-17). A run that needs more threads sets a number and counts them as processes.
- **Memory.** Before a run on a real route, `free -g` shows at least 20 GB available. The run is wrapped so that a runaway is killed alone, `systemd-run --scope -q -p MemoryMax=16G -p MemorySwapMax=0 <command>`, and the planner gets an explicit memory net of at most 12 GB where the command takes one (its default is 80% of the machine, 48 GB here, which several runs at once cannot all have). On 2026-11-17 and 2026-11-18 the machine's memory in use passed 55 GB of 60 three times (58.8 GB at the highest), and on 2026-11-17 the kernel killed one uncapped Python process of 54 GB.
- **Time.** The chat gives the run a limit (`timeout 90m ...`), about twice what it expects; the dispatcher's 60-minute cap is a rule for GitHub's runners, not for the server.
- **Re-records.** The run writes the files in the worktree and the chat commits them itself.
- **Waiting.** A job that may outlive its agent (a dispatch retry loop, a long measurement) is detached, `setsid nohup <script> > <log> 2>&1 < /dev/null &`, and its pid and log path go into the handoff file at once. An agent waits on a pid (`while kill -0 PID 2>/dev/null; do sleep 20; done`), never on `pgrep -f "<pattern>"`: the waiting shell's own command line holds the pattern, so the loop matches itself and never ends (an agent hung for hours on 2026-11-18).

GitHub keeps what the server does not give: a PR's own CI, the integration run that lands a PR (Ubuntu and Windows, unchanged), and a run that needs Windows. A heavy run on GitHub is for that last case, for when the server is full, or for a run that needs a quiet machine of its own per process (the heavy benchmark's record of the site's plans, under the time net: `docs/ci.md`, #1109), and goes **only through the dispatcher**: `python .github/scripts/heavy_dispatch.py run --ref <branch> --runners N --command '...'`, never `gh workflow run run.yml`. The repo has 20 runner jobs at once; the dispatcher waits until merge CI keeps a buffer (`HEAVY_FLOOR` and `CI_RESERVE`, repository variables), and refuses a timeout over 60 minutes unless `--long` (one indivisible solve). `python .github/scripts/heavy_dispatch.py status` shows the queue. Details: `docs/ci.md`.

Nobody polls a GitHub run inside a turn. The main chat dispatches with `--no-wait`; on exit 3 (no room now) it runs the command again later in the background. It waits with `python .github/scripts/wait_runs.py <run id>...` in the background (a chat that turned Auto-fix on for its PR is woken by it on that PR's CI). A helper (`finder`, `checker`, `crafter`, `auditor`) starts no heavy run. A re-record dispatched to GitHub with `--commit <paths>` commits its own files onto the branch.

## Talking to the owner

The owner is the product owner, not a developer: he decides what he wants and what he accepts, and he comes in cold between chats. Every reply to him:

- is in Russian; the first line answers what he asked or gives the result;
- says in plain words what physically happens: a path, a function name, a commit id becomes what it does;
- asks only what only he knows (what he wants, his taste, the money, time and risk he accepts), each question standing alone: the context, the options with their consequences, your recommendation; the rest you decide and say in one line with its reason;
- names what showed a thing is done: the test, the command, the file;
- writes time in minutes and hours;
- past three lines, ends with a short **TLDR**: what happened and what needs his answer.

He does no step you can do yourself: a command, a commit, a file edit, a merge.
