# Extending to new methods and patches

The owner requires flexibility across leagues ([#81](https://github.com/Rasslabsya4el/crafting-system/issues/81) Q11, 2026-10-31): new numbers in a league the same day, a changed rule of an existing method in a few hours, a brand-new method in one or two tickets, **without changes elsewhere in the system**. Until ticket [#108](https://github.com/Rasslabsya4el/crafting-system/issues/108) a new action touched `abstraction` (class lists and `isinstance` checks), `cli/_offers.py` (hand-wired offers and costs) and the cost rules of its own family. Now every action meets one contract, `actions` keeps a catalog, and everything else reads the contract.

## What each change touches

- **New numbers** (a weight, a price, a bench cost): the data pin (`data`, the patch-update skill) or the price file. No code.
- **A changed rule of an existing method**: its claim in `rules/claims/<family>.yaml` and, if the logic changes, the one action file and its tests. The cost of an orb or a reforge is a claim too (`chaos_orb.cost`, `harvest_reforge.lifeforce_cost`, ...), so a price-name change there is a claim edit; an essence, a fossil or a bench craft is priced under the name the game data gives it (`essence.cost`, `fossils.cost`, `bench_craft.option_cost`), so a new patch moves them with the data pin.
- **A brand-new method**: one file in `actions/` that subclasses `Action`, registers its kind with `@kind(...)`, and cites its claims; plus its tests. Nothing in `abstraction`, `cli` or `simulator` changes. A method that does not draw from a pool lists its results with `Finite`; one that draws uses `Outcomes`.

## The contract

An action answers five questions (`actions/contract.py`): `label(data)`, `outcomes(data, item)` (exact `distribution`, `chance_all` and `sample`, plus `components`, the mixture the kernel is built from), `resources(data)`, `reads(data)` and `adds(data, item)`. `abstraction` builds the state from the `reads` of the enabled actions and the kernel from `outcomes` alone; `cli` builds its offers from the catalog, `resources` and `adds`; `simulator` samples `outcomes`. `tests/test_actions_no_concrete_imports.py` fails when a module outside `actions` names a concrete action class.

A sixth question is optional: `twin_key(data, item)` (default None) is a cheap key such that two actions of one catalog listing with equal, non-None keys give equal `outcomes` on every item of that base, without building a pool. Sets of fossils declare it (12,696 sets of a boots item fall into about five thousand classes); `tests/test_actions_twin_key.py` checks that equal keys give equal outcomes, and pruning (#118) keeps only the cheapest of a class.

`reads` is the one declaration that must be right: an action that reads nothing of the other mods **erases** them, which is why a state need not store them. An action that declares nothing reads every mod and tells every family apart: exact, but the state count can blow up. A new method is therefore correct by default and fast by declaration.

## The catalog and the planner

Each module registers its kinds, with an order number and a `planner` flag. `catalog(data, item)` lists the actions that can apply to the item or to what a policy makes of it; `planner_only` leaves out the kinds the planner cannot use yet (Orb of Scouring, Orb of Alchemy; the Transmutation, Alteration, Augmentation and Regal Orbs became planner kinds with R13, #66), each with its reason. A kind can be `opt_in`: the planner can use it but offers it only when a target names it in `actions:` (the fossil sets, with R08 and R09, #63: a rare start would otherwise list 12,696 fossil sets). A new kind is offered by default. The planner's filters are over declarations, not classes: an action that only adds named crafted mods is offered when a mod it adds counts toward the target (the #60 rule), and an action that needs a crafted mod (`Reads.needs_crafted`) is offered when the start item holds one or another offered action adds one. Pruning for speed (#118) is a further filter over `adds` and `reads`; the claim history (#120) reads the claims.

Two more declarations carry decisions that used to hide in the CLI and in ADR-0023. `Adds.keeps_crafted` (default True, the safe value) says whether a crafted mod survives the action. A bench craft that gives the target nothing is left out; while every other offered action declares False that is exact, and once an offered action keeps the crafted mod (Augmentation, Regal Orb: R13, #66) it is a choice, not a proof, because a craft could take a slot or clear a family from the pool before the next orb (all 100 belt crafts offered make R13 a graph of more than 40,000 states after four minutes of search). The report then says that the plan is the cheapest among the offered crafts; the exact answer is for the pruning (#118) and the metamod work (#68). `Reads.block_invariant` (default False, refuse) says that the action's kernel, pushed through the pooling of junk families, is the same for every member of a block (ADR-0023, #125): it is set on the erasing rerolls (fossils included), the bench crafts and Remove Crafted Mods, and the contract suite compares the members of blocks on the fixture items. A `Finite` action is not invariant until someone proves it. `Reads.pool_weight` (set by `Reads.adding()`) is for an action that keeps the junk and adds mods (Augmentation, Regal, later Exalted): the state then tells junk families apart by family type, the weights they take out of the pool, not by name (ADR-0009, #65); an action that needs more says it in `Reads.families`.

The metamods (ticket #68) cost the compressed state no declaration of their own: ticket #69 removed `Reads.metamods`. `Abstraction(..., metamods=True)` (forced when an enabled action adds a lock or an Attack/Caster metamod by name, found through `Adds.named`) keeps every mod as a slot and reads from the action's own `outcomes` what a lock keeps and an Attack/Caster metamod filters, so a new action needs nothing for them. One declaration was added: `Reads.fractures` (default False) says that the action may fracture a mod the item already holds (a Fracturing Orb), so the state stores a fractured mod of a family told apart only by its family type as that type (ADR-0009, "Widening for removals, metamods, influence and new fractures").

## Limits a later ticket must lift with a contract change

- **Two-input actions** (ADR-0022): lifted at the contract by the amendment below (ticket #210): `inputs(data, item)` and `rule_axes(data)`. What it does not lift: the compressed state of a donor (#211), the solve with donors (#212), the interval over the readings (#220) and the simulator's nested runs (#222).
- **Implicits, quality and the unveil offer** were also outside the contract; [ADR-0027](0027-item-state-beyond-explicit-mods.md) (grill B2) lifts that limit by letting `Item` store them and `Reads`/`Adds` declare them (`implicits`, `quality`, `offer`; the compressed state keeps them when an enabled action reads or changes them: ticket #142).
- **In-place value changes** (a Divine-like orb, #71): lifted by the `Rerolled` part of `ActionOutcomes.components` (`actions/contract.py`: the item the action was given and the `(mod_id, fractured, crafted)` keys of the mods whose values are rerolled) with `Reads.rerolls_values`, so a kernel can tell a changed roll from a kept one; `actions/divine.py` is the first action to use it, and `Adds.needs_roll_limit` makes a planner offer such an action only for a target with a roll limit. Before it, the kernel accepted only `Fixed` or `Outcomes` parts and `_split` matched mods by `(mod_id, fractured, crafted)`, so a changed roll would have counted as kept. The Orb of Unravelling changes tiers in place the same way (ADR-0044).
- **`Adds` names only what is added by name** from the start item. For a drawn action it says that there is a draw, so pruning by proof (#118) goes through `outcomes` for those.
- **The catalog looks at the start item's rarity** (essences of level 1 to 4, the orbs of magic items): those kinds are not listed for states a policy reaches later. A normal start item lists Transmutation, Alteration, Augmentation and Regal Orb, which is all R13 needs; a rare start (R10, R11, R05, R12) lists none of them.
- **The catalog lists a Divine Orb only for a non-normal start item** (`divine.py`'s kind yields it for a magic or rare item): a normal start item gets none, though the orb would take it after a Transmutation; like the rarity limit above, it is not re-listed for states a policy reaches later.
- **Prices of essences, fossils and bench crafts** come from the game data's names, not from a claim's value; the claim says so.
- The contract suite does not compare a fracturing action (Fractured Fossil, Fracturing Orb) with the brute force; `test_abstraction_fossil.py` and `test_abstraction_fracture.py` do. The pilot count (`estimate`) and the family-group level (`Coarsening`) refuse a state that holds a fractured mod as a family type (`Reads.fractures`) and `Coarsening` also refuses a block that holds a lock or an Attack/Caster metamod. The kernel refuses a tagged reforge, a fossil that changes a weight or an essence that forces a mod of the same family type after a fracture that is held as a family type (ADR-0009).
- **Kinds offered only when named, and single actions named by label (ticket #70).** A kind with `opt_in` (the fossil sets, #61) is a planner kind that a query lists only when the target's `actions:` names it; the Exalted Orb, the Orb of Annulment, the Fracturing Orb and the corrupted essences are opt-in kinds too (ticket #70), so adding the Exalted Orb, the Orb of Annulment, the Fracturing Orb and the four corrupted essences (`corrupted-essence`) did not change what R10, R11, R05, R12 and R13 are offered. Those kinds list their action for a normal and a magic start item too, because the item becomes rare on the way. A name in `actions:` that is not a kind is the label of ONE action (`Essence of Insanity`, `Bench craft Cannot roll Attack Modifiers`): it is offered whatever the other filters say (a metamod craft counts toward no requirement and the craft filter would drop it), and of a kind not named as a whole only the actions named by label are listed. A name that is neither is refused with the kinds there are.

## Verification

`tests/contract_support.py` runs on every kind of the catalog without being edited: outcomes sum to one; the finished items listed from `components` give each mod the chance `chance_all` says; the sampler follows it within five standard errors; the kernel equals the brute force on the compressed finished items (layer 1, ADR-0019); what an action declares agrees with what it does; its resources price an offer from a fixture price file; its label round-trips through a given route. A toy action defined only in `tests/test_actions_toy.py` is offered by the CLI, gets exact kernels, runs in the simulator and passes the same checks, which is the test that the contract is enough.

## Rejected

- A `typing.Protocol` alone: a new method could forget `reads` and silently be wrong. The base class gives the safe defaults.
- Kernel dispatch on the kind of outcome (a bench result, a resonator result): every new shape would need a kernel edit. The kernel reads the mixture of parts (`Fixed` or a pool draw) that every outcome exposes.
- The planner choosing actions by class or by a list in `cli`: the toy action would need an edit there.

## Amendment: foresight in the contract (B8, [Grill B8](https://github.com/Rasslabsya4el/crafting-system/issues/106), 2026-11-01)

The contract gains three optional declarations, each with a safe default: `previewable` (default `no`) with `currency_item`, which say whether and as what an action is an option of a Lock (ADR-0055), and `burn` (default False), which says that the action changes no mod and may give a Lock up (ADR-0056). A new kind, `HinekoraLock`, sits beside `Action` for the Lock itself: a label, a legality test (corrupted, mirrored and unmodifiable items refused) and its resources, and no outcomes of its own, because the Peek of ADR-0054 builds them from the options. Nothing outside `actions` names a concrete action.

## Amendment: inputs and rule axes in the contract (B3, [ticket #210](https://github.com/Rasslabsya4el/crafting-system/issues/210), 2026-11-01)

The contract gains two optional questions, each with an empty default, so an action that has neither is untouched (the outputs of B1 are byte-identical, `tests/test_b1_unchanged.py`) and a new kind is still correct by default.

- `inputs(data, item)` returns a tuple of `Need(start, want)`: the other items one use consumes, each given by the item it begins as and the item it must become (ADR-0022). A repeated `Need` is a second copy. The action finds its donor in `outcomes` by asking the same question, so `outcomes(data, item)` is the exact result of using it with those inputs; `Abstraction.inputs(state, action)` asks it for the item a state stands for. `Reads.input_mods` says that the result depends on the mods of the inputs, beside or instead of those of the item in hand (`junk`); the dataclass default is False and the default of `Action.reads` is True, as for the other fields.
- `rule_axes(data)` returns a tuple of `Axis(name, readings, plan)`: the rules the action reads that the sources leave open (ADR-0033). `outcomes(data, item, reading=None)` of such an action takes a `Reading`, one value per axis, and uses the plan's value for an axis the reading lacks, so the simulator, which calls `outcomes(data, item)`, samples the plan. Callers use `outcomes_under(data, item, reading)`, which hands the reading to an action that has axes and calls the others as they always were. `model_readings(data, actions)` lists the readings of a model, the plan's first (the product of the axes by name; two actions that name one axis must agree on its readings). An `Abstraction(..., reading=...)` is the ordinary model of one reading: its kernels are taken at it, and nothing else in `abstraction` or `solver` learns what an axis is.

`catalog` and `planner_only` list the kinds of such actions like any other (a kind the planner cannot use yet is registered with `planner=False` and its reason). The planner, until the solver is given the donors (#212) and the interval driver exists (#220), keeps the stop in two places: an `Abstraction` made with `allow_inputs=False`, which `make_plan` does, refuses an action whose item has inputs with `OutOfScopeError` (so a graft is never priced with a free donor and the planner treats it as unavailable), and `make_plan` raises `PlanError` for an offered action that reads an axis. An `Offer` carries the `inputs` (of the start item) and `axes` of its action. `tests/contract_support.py` runs every check at every reading of the action's axes and checks that `inputs` are valid `Need`s, the same on every call, and that `outcomes(data, item)` is the plan's reading; `tests/test_actions_inputs.py` is the toy: a two-input action (a donor, an axis of three readings) offered by the CLI, with exact kernels per reading, passing the suite, defined only in `tests/inputs_support.py`. `tests/test_actions_no_concrete_imports.py` still holds.

## Amendment: corrupting actions in the contract (B4, [Grill B4](https://github.com/Rasslabsya4el/crafting-system/issues/95), ticket #258)

`Adds` gains two declarations, both False by default: `corrupts` (the action corrupts the item and adds a corrupted implicit, so it needs `implicits` too; every outcome is a corrupted item, which is final: the goal or a dead end, ADR-0036) and `keeps_mods` (with `corrupts`: every outcome that can still be the goal of a target that asks for a corrupted implicit holds the explicit mods the item held; a resonator that rerolls them leaves it False). `Adds.corrupting(keeps_mods=...)` builds both. The offer filter keeps a corrupting action only when the goal takes a corrupted item (`Goal.asks_corrupted` or `Goal.allow_corrupted`, read from the target); a kind whose actions all corrupt registers with `corrupting=True`, and the report leaves it unmentioned for a target that takes no corrupted item; for a target that asks, `solver_actions` offers a corrupting action that keeps the mods only from a state that meets every other requirement (`Abstraction.meets_requirements`), an exact pruning (ADR-0031). `Abstraction.is_goal` follows `Target.is_met_by`: a corrupted state is a goal only where the target takes corruption, and an uncorrupted state is no goal of a target that asks. The compressed state keeps no corrupted implicit (it skips one when it compresses an item, ADR-0036), so what the state can tell a goal from a dead end is the explicit mods and the Eldritch implicits. Telling a corrupted result that holds the asked corrupted implicit from one that holds another is not in this ticket: it needs the implicit state of #152 and #158 and is the kernel of the Vaal Orb (C5, #259), which builds on `Goal.asks_corrupted`; until then the planner refuses a target with implicits, and the toy of the tests makes its dead end an outcome that loses the explicit mods. The contract suite checks that an action corrupts only when it says so, that every result is corrupted and that no action of the catalog applies to one, and that a `keeps_mods` action reaches no goal of an asking target from a state that misses a requirement. `tests/test_actions_corrupting_toy.py` defines a toy corrupting action that passes the suite.
