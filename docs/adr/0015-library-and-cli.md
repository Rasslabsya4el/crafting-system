# v1 is a Python library and a CLI: YAML in, JSON policy and text tree out

v1 has no HTTP service (**replaced as the description of the product: see "Amendment: the product is a website" at the end**). Its one HTML output is the route view (below). Input is a YAML target file: base, item level, influence, requirements by English stat text or family id with a minimum tier or roll, k-of-n requirements, an optional start item, the price file path. Output is a JSON policy (for each state reachable under it: the action, the expected remaining cost, the chance to get there, the transitions) and a short text tree in the terminal (the main line, where to go on a miss, odds, mean cost, p90). Modifier text is English.

The route view ([Route view: the policy as an HTML page with item states](https://github.com/Rasslabsya4el/crafting-system/issues/78), look settled with the owner in [How a multi-step policy reads in the terminal](https://github.com/Rasslabsya4el/crafting-system/issues/58)): `python -m crafting_system.cli TARGET.yaml` also writes `<output dir>/<target>.route.html`, one self-contained page (no script, no external file, no request; light and dark by the browser's setting) that the chat shows to the owner, since he reads only the chat. The text tree and the JSON policy stay. The page is built from the same policy: a goal card, then one row per step, the step card (the exact action, its goal, chance per use, cost, uses on average, where a miss goes) beside the item card of the state after it. A step stands for a set of compressed states only when the policy takes the same action in all of them *and* the same chances into the same steps; look-alike states that need different actions or different chances are separate steps, so the page never says "while a prefix is empty" without showing what happens when none is. A buy step carries a link to the official trade site's search, built from the buy spec (`--buy-spec`) with the query code of `prices`; the owner opens it, the program never requests it. With `--route` the given route is drawn in the same view, its gaps as steps with no action. The HTML is not a report format with a service behind it: one file per query, no server (**replaced for the product by the same amendment**).

Built in [R12 end to end: CLI, JSON policy and text tree](https://github.com/Rasslabsya4el/crafting-system/issues/26): `python -m crafting_system.cli TARGET.yaml` prints the text and writes the JSON (the format is `crafting-system-policy/1`, since ticket #459 `crafting-system-policy/2`, where `limits` replaces `left_out_actions`, `dropped_actions` and `note`: totals with certified intervals, and per state the action, its cost, the expected remaining cost, the chance the policy ever gets there and the transitions), and since ticket #630 `crafting-system-policy/3`, where `requirements` is `{"plain": [...], "groups": [{"at_least": k, "of": [...]}]}` (a k-of-n group stays a group, each member with its `side`; `/2` listed every member of a group as a plain requirement). `--verify` runs the simulator on about 10,000 concrete crafts and agrees when its mean is within five standard errors of the computed one; its interval is a normal approximation. The report and the command line are one package, `cli`.

Origin: [Design grill round 2: data, batches, repo](https://github.com/Rasslabsya4el/crafting-system/issues/3) Q15.

Since ticket [#880](https://github.com/Rasslabsya4el/crafting-system/issues/880) the library has two parts where this ADR said "report / cli" (ADR-0018, its amendment). The **planner** (`crafting_system.planner`) is the library proper: `plan_target(data, target, prices, settings)` returns the plan and does no input or output. The **report / cli** module (`crafting_system.cli`) is the command line around it: it reads the YAML target and the price file, calls the planner's entry, and writes the three outputs named above (the text tree, the JSON policy, the route view). What this ADR says of the inputs and the outputs is unchanged.

## Considered options

- The old prototype's HTML report and an HTTP service: out of v1; Docker comes only with an HTTP service (ADR-0014). The one HTML file of the route view is the exception, because the owner reads only the chat and the look he accepted needs a page.

## Amendment: the product is a website ([#900](https://github.com/Rasslabsya4el/crafting-system/issues/900), owner rules OR-35 and OR-36 in [`docs/owner-rules.md`](../owner-rules.md), 2026-11-13)

The sentences above that "v1 has no HTTP service", that the route view is "one file per query, no server", and the option below that puts an HTTP service out of v1, are replaced as the description of the product. By the owner's rules of the retro of 2026-11-13:

- **OR-35.** The product is a public website in November 2026: the user builds an item as on Craft of Exile, picks the crafting methods the run may use and an economy mode, starts the run and gets a route page.
- **OR-36.** Every generated route is stored and listed on the site, and an identical request is answered from the store.

What stands of this ADR: the library, with the planner's one entry, and the command line around it with its YAML input and its three outputs. The tests and the chats use them, and the site calls the planner's entry (ADR-0018, its amendment). How the site is built (its modules, its store, the Docker of ADR-0014) is not decided here; it is the dispatcher chat's decision (OR-50) and gets an ADR of its own.
