# v1 is a Python library and a CLI: YAML in, JSON policy and text tree out

v1 has no HTTP service. Its one HTML output is the route view (below). Input is a YAML target file: base, item level, influence, requirements by English stat text or family id with a minimum tier or roll, k-of-n requirements, an optional start item, the price file path. Output is a JSON policy (for each state reachable under it: the action, the expected remaining cost, the chance to get there, the transitions) and a short text tree in the terminal (the main line, where to go on a miss, odds, mean cost, p90). Modifier text is English.

The route view ([Route view: the policy as an HTML page with item states](https://github.com/Rasslabsya4el/crafting-system/issues/78), look settled with the owner in [How a multi-step policy reads in the terminal](https://github.com/Rasslabsya4el/crafting-system/issues/58)): `python -m crafting_system.cli TARGET.yaml` also writes `<output dir>/<target>.route.html`, one self-contained page (no script, no external file, no request; light and dark by the browser's setting) that the chat shows to the owner, since he reads only the chat. The text tree and the JSON policy stay. The page is built from the same policy: a goal card, then one row per step, the step card (the exact action, its goal, chance per use, cost, uses on average, where a miss goes) beside the item card of the state after it. A step stands for a set of compressed states only when the policy takes the same action in all of them *and* the same chances into the same steps; look-alike states that need different actions or different chances are separate steps, so the page never says "while a prefix is empty" without showing what happens when none is. A buy step carries a link to the official trade site's search, built from the buy spec (`--buy-spec`) with the query code of `prices`; the owner opens it, the program never requests it. With `--route` the given route is drawn in the same view, its gaps as steps with no action. The HTML is not a report format with a service behind it: one file per query, no server.

Built in [R12 end to end: CLI, JSON policy and text tree](https://github.com/Rasslabsya4el/crafting-system/issues/26): `python -m crafting_system.cli TARGET.yaml` prints the text and writes the JSON (the format is `crafting-system-policy/1`: totals with certified intervals, and per state the action, its cost, the expected remaining cost, the chance the policy ever gets there and the transitions). `--verify` runs the simulator on about 10,000 concrete crafts and agrees when its mean is within five standard errors of the computed one; its interval is a normal approximation. The report and the command line are one package, `cli`.

Origin: [Design grill round 2: data, batches, repo](https://github.com/Rasslabsya4el/crafting-system/issues/3) Q15.
